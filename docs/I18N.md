# Languages, regional formats and phone numbers

## What is implemented
| Language | Code | Direction | Status |
| --- | --- | --- | --- |
| English | `en` | LTR | Source language |
| French | `fr` | LTR | Beta: **translation pending professional review** |
| Spanish | `es` | LTR | Beta |
| Portuguese | `pt` | LTR | Beta |
| German | `de` | LTR | Beta |
| Arabic | `ar` | **RTL** | Beta |
| Hindi | `hi` | LTR | Beta |

These are the only languages offered. Languages such as Chinese, Japanese, Korean, Russian, Turkish, Indonesian, Bengali, Urdu, Italian, Dutch, Swahili, Hausa, Yoruba and Igbo are **not implemented**; the framework is built so each can be added without touching components (below), but no translation for them exists and none is advertised.

The non-English texts were written by the engineering team, not by professional translators, and have not been reviewed. Financial, security and legal wording in particular needs a native-speaking professional before any of these languages is described as fully supported. The selector labels every one of them "Beta" and shows its coverage.

## What is translated
Catalog keys (`frontend/src/locales/*.js`, 184 keys per language) cover: public navigation, sign-in, registration (labels, hints, client-side validation messages), the phone field and country picker, the language picker, the account menu, the log-out confirmation, the session-lock screen, the profile header, the dashboard greeting, the whole Settings hub (menu, display page), the transfer options, the To EWB form and the savings messages.

**Still English in every language** (falls back to English, never to a raw key): most dashboard cards, accounts, transactions, withdrawals, notifications, the admin console, the legal documents and public marketing text (those come from the API and the admin-editable CMS), and every message produced by the server (API errors, emails). Translating them means moving each string into the catalogs and adding it to every language.

## Architecture
* `src/lib/i18n.js`: language registry (code, English name, native name, direction, regional locale), `t(key, vars)` with `{placeholders}`, plural keys (`key_one`/`key_other`… via `Intl.PluralRules`), English fallback, a `missing` set that records untranslated keys, and `coverage(code)`.
* Components call `usePrefs().t`, so the page re-renders when the language changes; nothing reloads and nobody is signed out.
* **Add a language:** create `locales/<code>.js` with the same keys, import it in `i18n.js` and add one registry entry, then add the code to `LANGUAGES` in `backend/src/services/preferencesService.js`. A test fails if a catalog has unknown keys.
* **Persistence:** signed-in customers: saved in `user_preferences.language` (server is authoritative). Visitors: `localStorage` (`ewb.prefs`, non-sensitive); `theme-init.js` applies `lang`/`dir` before the first paint.
* **RTL:** the document gets `dir="rtl"` for Arabic; layout rules in `layout.css` mirror the sidebar, drawer and active markers, flip directional chevrons (`flip-rtl`), and keep phone numbers, emails and account numbers left-to-right.

## Regional formatting
"Match my device" now follows the chosen language (French: `1 234,56`; German: `1.234,56`; Hindi: lakh grouping; dates in that locale). An explicit choice under Settings → Timezone & regional formats still wins. Only the **display** changes: stored amounts are integer minor units in each account's own currency, and the language never converts, rescales or relabels a currency.

## Phone numbers
* Validation uses `libphonenumber-js` (per-country rules, not a fixed digit count), on the client for fast feedback and **again on the server**, which is the authority.
* Stored as E.164 in `users.phone_e164` (unique partial index); `users.phone` holds the same value for new numbers. The selected country's dial code must match the number.
* A number can belong to one profile only; concurrent sign-ups are settled by the unique index.
* **Legacy customers** keep their records (nothing is invented). `phoneRequired` is true for them, the app shows a banner asking for a valid number, and changing it needs the account password. `node src/db/backfillPhones.js` (dry run by default) can normalise legacy values that are already valid international numbers.
* **Verification is not implemented.** The product has no SMS provider (`NullSmsProvider` only). Numbers are stored as *unverified* and nothing says otherwise. To add verification: choose a provider (Twilio Verify, Vonage Verify or, for Nigerian routes, Termii), add credentials as server-side environment variables (for example `SMS_PROVIDER`, `SMS_ACCOUNT_SID`, `SMS_AUTH_TOKEN`, `SMS_SENDER_ID`), implement `SmsProvider.send/verify` in `providers/regulated.js`, and set `phone_verified_at` only after the provider confirms a code. SMS delivery is a paid service and may need sender registration per country.
